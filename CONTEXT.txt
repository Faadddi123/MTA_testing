1. WHAT THIS PROJECT IS

This repository is not a normal greenfield app. It is a Multi Theft Auto (MTA) Linux server distribution for GTA San Andreas, with a custom roleplay layer added on top of the stock MTA resource tree.

The important distinction is:

- Most of `mods/deathmatch/[admin]`, `[editor]`, `[gamemodes]`, `[gameplay]`, `[managers]`, and `[web]` is stock MTA content.
- The actual project-specific logic lives primarily in:
  - `mods/deathmatch/resources/[core]/database_manager`
  - `mods/deathmatch/resources/[systems]/bank`
  - `mods/deathmatch/resources/[systems]/inventory`
  - `mods/deathmatch/resources/[systems]/housing`
  - `mods/deathmatch/resources/[systems]/vehicles`
  - `mods/deathmatch/resources/[systems]/garage_system`
  - `mods/deathmatch/resources/[systems]/house_manager`
  - `mods/deathmatch/resources/[maps]/open_interiors`

If another model needs to understand the real project, it should start with those resources, not the stock gamemodes.

4. WHAT THE CUSTOM MODS / RESOURCES ACTUALLY DO

4.1 `database_manager`

Purpose:
- Central RP database layer.
- Owns the authoritative SQLite file: `roleplay.db`.
- Normalizes player identity into `owner_key`.
- Exports helpers used by every other system.

Core idea:
- A player identity is stored as either:
  - `account:<accountName>`
  - `serial:<hardwareSerial>`

This lets the project support guest/serial-backed temporary state and then merge that into account-backed state on login.

Main exports:
- `dbExecute`
- `dbQuery`
- `getPlayerOwnerKey`
- `ensurePlayerRecord`
- `ensureOwnerRecord`
- `isMigrationComplete`
- `markMigrationComplete`
- `hasPropertyKeyAccess`
- `grantPropertyKey`
- `revokePropertyKey`

What happens on player lifecycle:
- On join: ensures a player record exists.
- On login: merges `serial:*` ownership into `account:*`.
- On quit: updates the player record again.

Main tables it creates:
- `players`
- `items`
- `houses`
- `property_keys`
- `vehicles`
- `migration_state`


4.2 `bank`

Purpose:
- Simple bank system using `players.bank_balance` in the central database.

Key behavior:
- Adds bank markers/blips at Los Santos, San Fierro, and Las Venturas.
- `/balance` works anywhere.
- `/deposit <amount>` and `/withdraw <amount>` only work when standing in a bank marker.
- `/setbank <player> <amount>` is admin-only.

Design detail:
- Bank balances are not stored in `bank.db` anymore as the authoritative source.
- `bank.db` is now only legacy migration material.


4.3 `inventory`

Purpose:
- Central item storage and UI.

Server side:
- Stores items in `items(owner_key, item_name, amount)`.
- Supports item normalization, dynamic item labels, icon mapping, and weight calculations.
- Uses central owner records.
- Admin commands:
  - `/inventory`
  - `/inv`
  - `/giveitem <player> <item_name> [amount]`
  - `/takeitem <player> <item_name> [amount]`

Client side:
- Press `I` to open the browser-based inventory UI.
- Inventory UI is rendered from:
  - `web/index.html`
  - `web/main.js`
  - `web/style.css`
- House interaction popup is not browser-based anymore. It is drawn with `dxDraw` directly in `inventory/client.lua`.

Dynamic item logic:
- `property_key_<houseId>` items are treated specially:
  - custom icon
  - custom label like `Property Key #7`
  - low fixed weight


4.4 `housing`

Purpose:
- Core property ownership and enter/exit system.

Responsibilities:
- Loads houses from the central `houses` table.
- Creates exterior markers, interior exit markers, and map blips.
- Lets players buy properties.
- Lets owners and key holders access locked properties.

- Supports previewing unowned houses.
- Gives new logged-in accounts a free apartment one time.

Important spatial model:

Player-facing commands:

4.5 `vehicles`

Purpose:
- Persistent vehicle storage using the same central database.

Responsibilities:
- Stores persistent vehicles in `vehicles`.
- Respawns non-garage vehicles on resource start.
- Saves vehicle state on park and on player quit.
- Links vehicles to garages if parked inside a valid owned garage zone.
- Spawns garage vehicles on demand.
- Despawns garage vehicles when the garage empties.

Commands/events:
- `/park`
- `/mycars`
- `vehicles:requestPark`

Storage model:
- If `house_id IS NULL`, vehicle is a world-stored persistent vehicle.
- If `house_id` is set, it is a garage-linked persistent vehicle.

Commands:

Dependency direction:

13. DETAILED END-TO-END EXPLANATION OF HOW EVERYTHING FITS TOGETHER

At startup, MTA reads `mtaserver.conf` and brings up a mix of stock resources and custom roleplay resources. The first important custom resource is `database_manager`, which opens `roleplay.db`, creates the RP tables if they do not exist, and establishes the `owner_key` identity model. That identity model is the glue for the entire server: inventory, bank, houses, keys, and vehicles all hang off it.

When a player joins, `database_manager` creates or refreshes a row in `players`. If they are not logged into an MTA account, the identity can fall back to `serial:<playerSerial>`. When they do log in, the system merges serial-backed state into `account:<accountName>`. That is why `database_manager` matters more than any other custom resource: it is doing both schema management and identity normalization.

The bank system is intentionally thin. It does not have its own real domain model anymore. It simply reads and writes `players.bank_balance`, wraps that in commands and bank markers, and uses `database_manager` to make sure the current player has a stable owner record. In other words, bank is just a specific UI and command layer around one column in `players`.

The inventory system is the next major subsystem. On the server side, it reads and writes the `items` table. On the client side, it opens a browser-based backpack panel with `I`. The browser UI is isolated to the inventory itself. The house interaction popup that appears near properties is no longer the browser UI; it is now a custom `dxDraw` overlay inside `inventory/client.lua`. That means this resource currently owns two separate user-facing presentation layers: browser HTML/CSS/JS for the backpack, and direct MTA rendering code for contextual house/garage hints.

Housing is the main gameplay subsystem. It loads every row from `houses`, creates the world-space exterior markers and interior exit markers, and teleports players between them. Each property has a private MTA dimension, typically `6000 + house_id`, so players inside separate properties never overlap. Buying a house changes `owner_key`, `owner_account`, and `locked` in SQL. Access checks are based on owner identity and, in theory, property keys. The same resource also contains the one-time free apartment grant for newly logged-in accounts.

Vehicles are persisted separately but are still tied into the housing layer. When a player parks a vehicle, the vehicles resource looks at the car position and asks the housing resource whether it sits inside an owned garage zone. If yes, the vehicle record gets a `house_id` and becomes a garage-linked vehicle. If not, it remains a general persistent world vehicle. World vehicles are auto-respawned on resource start; garage vehicles are spawned only when someone is actually inside the relevant garage.

Garage logic is split into its own resource. It reads garage coordinates from housing, constructs garage markers and blips, teleports players into a garage dimension (`7000 + house_id`), tracks how many people are inside, and asks the vehicles resource to spawn or despawn garage-linked vehicles based on occupancy. Conceptually, housing owns the data model, vehicles owns persistence, and garage_system owns the garage-session runtime behavior.

House creation and editing are handled by `house_manager`, which is an in-game admin GUI. It is effectively a content management tool for the `houses` table. The server script contains the preset interior catalog. The client script contains the GUI, preview buttons, delete confirmation, edit fields, and teleport buttons. When an admin creates a property, the resource captures their current world position as the exterior, picks an interior preset, generates a property dimension, creates garage coordinates relative to the admin's facing angle, inserts everything into SQL, and then restarts `housing` so the new markers and blips are rebuilt.

`open_interiors` is separate from housing. It is a static map resource that exposes specific always-public buildings using the stock `interiors` resource. It does not depend on ownership or the `houses` table. It exists to make certain public RP buildings available even though the main housing system is reserved for buyable instanced properties.

The stock MTA folders remain present and runnable, but they are not the custom project. They are infrastructure. The custom project is the roleplay layer composed of the core DB resource plus the systems resources listed above. If another model starts editing race maps, default gamemodes, or stock admin files without a very explicit reason, it is almost certainly working in the wrong place.

In short, the project is a custom MTA roleplay server whose real architecture is:

- `database_manager` = identity + schema + persistence root
- `bank` = money storage UI over `players.bank_balance`
- `inventory` = item storage + browser UI + house popup UI
- `housing` = property ownership, dimensions, buy/enter/lock logic
- `vehicles` = persistent vehicle storage and park logic
- `garage_system` = garage teleports and on-demand garage vehicle spawning
- `house_manager` = in-game property authoring/admin tool
- `open_interiors` = static public interior entrances

That is the project another model should carry in its head before making changes.
